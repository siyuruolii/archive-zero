# 工程失败与经验

记录与项目实现相关的现象、已确认原因、未证实假设、修复与复验。编号保留历史身份，个人准备和一次性本机维护记录不纳入项目文档。完整原始记录已在本地保留，历史验收不代表当前模型质量。

## F001：权限变化后仍复用读取拒绝结果

- 日期：2026-10-25，第一阶段本地测试。
- 现象：先读取未授权历史正文得到拒绝；随后合法展开历史，已获得读取资格，但再次读取仍被拒绝。
- 影响：合法工具循环无法继续读取历史原文。
- 证据：首轮测试 74 通过、1 失败；`tests/test_tools_context.py::test_history_scope_and_read_access`。
- 已确认原因：工具缓存保存了权限错误；授权集合变化后，同参数请求仍命中旧拒绝结果。
- 修复：仅缓存成功的只读结果，不缓存权限或可用性错误。
- 复验：同一用例覆盖“先拒绝 → 合法展开 → 再读取成功”，已通过；最近整套本地测试 78 通过、6 个真实用例跳过。
- 经验：请求参数相同不意味着授权状态相同。缓存键和缓存策略必须考虑可变前提，不能只验证静态权限。
- 状态：本地回归通过。

## F003：真实路由响应触发 SSE 总传输限制

- 日期：2026-10-25，用户在已配置 DeepSeek 的独立终端执行真实测试。
- 现象：6 项中 3 通过、3 失败，耗时约 47.9 秒。三个路由用例均为 `provider_stream_size_limit`；正文精读、缺正文失败处理和讨论用例通过。
- 影响：路由任务未取得可接受的最终结果，第一阶段不能宣布整体验收通过。
- 证据：`artifacts/stage1-live.xml` 的首次报告。该路径会被下次运行覆盖，因此这里保留首次结果摘要。首次报告没有模型名称、原始流或最终输出，不能据此判断具体模型版本及内容质量。
- 已确认原因：程序累计的流字节数超过原来的 256 KiB 限制，适配器主动拒绝响应。
- 待确认解释：重复事件元数据可能使传输体积远大于实际生成内容。新增本地回归已证明这种合法流会触发旧限制，但没有原始流证据证明本次实际响应的字节构成，不能把推测写成已证实根因。
- 修复：总传输上限改为 8 MiB，新增单 SSE 事件 64 KiB 限制；单轮生成结果 32000 字符及调用/用时预算保留。
- 本地复验：新增元数据较多、超过旧上限但输出短小的模拟 HTTP 流用例，以及单事件超限用例。整套结果 78 通过、6 个真实用例跳过，静态检查通过。
- 待办：在已配置终端重新执行六个真实用例，检查安全结果文件中的模型身份、最终结构、摘要依据和阅读范围。若仍失败，依据新结束原因继续定位，不预先认定扩大上限已解决实际服务问题。
- 经验：传输预算、单事件内存预算和生成内容预算分别设置；本地模拟应覆盖流式协议的元数据开销；结构测试通过仍需真实服务验证。
- 状态：代码已修复、本地回归通过，真实复测待完成。

## F008：中文多段正文触发过于保守的输入预算

- 日期：2026-11-07，用户截图反馈。材料“一个 agent 同时干很多活，靠的是系统结构”路由失败，错误为 `context_budget_exhausted`；同库还有三条同类错误。
- 现场证据：该材料来源简介只有 122 字符，主题描述很短。旧程序以序列化请求 UTF-8 字节数加输出预留直接对比 32768 上限；中文多段工具结果会累积约三倍字符数量的字节开销。旧错误没有保留具体调用轮次，不能断言截图中某次工具返回的大小。
- 复现：新增中文 20000 字符、五段各 4000 字符阅读的受控用例；旧 32768 配置确实提前拒绝，新的有界默认配置可以完成六次模型轮次。此复现支持预算过于保守的判断，但不冒充用户原任务的真实服务重放。
- 修复：默认 UTF-8 代理上限改为 131072，仍保留输入、输出预留、模型/工具次数和总用时限制。保留历史字段名兼容，但明确它不是精确 tokenizer。运行报告记录每轮输入字节、预留和上限；后续路由超限显示这些诊断值。
- 保护检查：超大初始简介仍在请求模型前拒绝，不删除历史、不伪造精读范围，不关闭预算。
- 验证：见 `tests/test_context_capacity.py` 和本轮 `artifacts/context-capacity-tests.xml`。没有对用户原任务进行远程重跑；需要明确退出旧桌面进程后重启，再对失败材料手动重试路由。重复获取会按现存材料去重，不会自动重试旧失败。
- 经验：区分字符、UTF-8 字节和模型 token。固定短样例通过不足以覆盖真实长文的多段读取；错误记录需要带实际预算数值。

## F009：精读分段合并被误判为非法结果

- 日期：2026-11-07，用户反馈“先让 agent 自证，再用代码做计划：pstack”精读报 `invalid_final_result`。

- 确认原因：工具实际读取 `[0,4000)`、`[4000,7111)` 两段，模型合法报告合并范围 `[0,7111)`；旧程序要求每条范围与某次工具调用严格相等，拒绝了等价覆盖。证据在 `artifacts/deep-diagnostic/result.json`。这不是“没读正文”，也不是 JSON 结构不合法。
- 修复：按当前材料的字符区间并集合对比，允许合并相邻/重叠区间或等价分段；跨未读缺口、超报、漏报、其他材料、部分阅读不说明限制仍拒绝。不替模型伪造读取范围，不关闭结果校验。
- 诊断补充：`runtime.py` 分开记录字段类型错误与业务约束错误，只保留字段/错误类型，不记录密钥或整份输入；`materials.py` 将诊断带入精读失败状态与操作回执。
- 本地复验：新增 `tests/test_deep_coverage.py`，调整旧重叠读取用例为检验真实字符集合，整套 113 通过、9 个真实用例默认跳过，静态检查通过。历史“缺失已读范围”仍有负例覆盖。
- 真实定向复验：结果保存在 `artifacts/deep-diagnostic/retest.json`；按实际运行状态追加，不将本地回归等同真实通过。
- 经验：阅读证据应比较已读字符集合，不能把工具调用的分页形状强加给模型最终表达；笼统 `invalid_final_result` 不足以定位字段或业务约束错误。

F009 真实复验补记：同一隔离材料的真实 DeepSeek 调用已返回 `succeeded/completed`，3 次模型请求、2 次正文读取，覆盖仍为 `[0,4000)` 和 `[4000,7111)`，没有校验错误。正式数据库保持未改动，用户须退出旧后端并重启后，在原材料上重试精读。
